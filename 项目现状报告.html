04还缺什么（按优先级）

对照 DESIGN.md 完整版 · pipeline.md v5 蓝图 · 路线存档 P0-P1
缺口状态说明与出处
PG/pgvector 正式存储换装 未做 DM7 决策的过渡态：数据态（documents/chunks/summaries/候选/证据）目前全部在 SQLite data/app.db。Store 接口已预留，但 PGStore 仅雏形 rag/ 里有，后端未接。影响：规模上限、向量索引性能、任务态/数据态分离未落地。
六元组的其余四段 部分 目前只落地 identity（identities 表+审批）与 ontology（persona_ontology 段+版本管理）。actions / guardians / interface 三段无任何表结构与封装——即「领域专家模板写死三段、部门填三段」的模板机制未开始（pipeline.md §3/§7）。
反思层（第六原语） 雏形 Benchmark 归因→merge→版本化是「数据驱动的定向反思」，但通用 Reflection（Trace 采集 → R1-R6 六类改进提名 → 确定性回归重放 → 分级固化 → 回流重编译）未实现，且 pipeline.md §9.3 明确「反思触发条件待定义」。对话结束异步复盘、Insight 对象、守护规则不可自我修改等约束均未编码。
需求编写人（P0 数字人）的动作面 未做 本仓库是「知识包构建工具」，产出数字人的先验知识；而 requirement writer 的提名-裁决管线（需求条目/澄清请求/提名轨迹、6 动作、状态机、文档组装导出）在路线存档中属于 myClaudeCode 工程，本仓库没有承接。两边尚未打通：本体段如何打包交付给数字人运行时没有接口。
通路库 + 事件模板化 未做 pipeline.md §1 核心模型——「任务进来→查通路库→命中套用/未命中创建」、标签优先 0 次 LLM 的事件识别、模板沉淀回流，完全没有实现（这是数字人编排层的入口）。
多数字人协同编排 未做 「找数字人→编关系→编协作流程+约束」四步、数字人↔数字人 Link、平台级/部门级两层体系、部门本体引用平台本体（禁止改写）的分级管理，均为设计态。
定时任务 / 分时用模 R9 未做 DESIGN.md §5.5/§6.5 规划的调度器与分时路由，MVP 明示搁置；当前所有 job 均手动触发。
本体分解器完整版 简化 现用 EDC-lite；pipeline.md §9.2 规划的「无模式 EDC + 基于模式 GraphRAG → 规范化 → ontology.yaml 产物」未收敛（文档标注「方案待确认」）；GLM 5.2 归纳核验只以分诊/判卷形态局部使用。
扫描件 OCR 未做 PDF 仅文本层，扫描件标记跳过并提示（MVP 范围外）。
首启向导 /setup 简化 DESIGN_MVP §5.1 的三步向导未做独立路由，以 SettingsPage + 首页引导替代；图谱渲染用自绘 SVG 而非 Cytoscape.js（功能等价，大规模图谱布局能力弱）。
优先级建议（供参考）：① PG/pgvector 换装（Store 接口已在，越晚迁移数据包袱越大）；② 六元组 actions/guardians/interface 模板化（这是「数字人工厂」复用机制的地基）；③ 反思触发条件定义 + Benchmark 回路泛化（pipeline.md §9.3 是唯一标「待定义」的设计空洞）；④ 与 myClaudeCode 需求编写人打通交付接口（ontology 段导出/导入格式）。

05三条铁律的代码级落地情况

铁律落地证据
① 绝对准确（证据可引） 证据关：mention/quiz/quote 必须逐字命中 chunk 原文（span 落库）；benchmark 判卷含拒答词检测；结论由代码模板生成，无 LLM 参与。
