# 04 · 阻塞缺陷：本地 Ollama 对话 100% 失败（0.3 秒返回「300 秒超时」）

> **结论先说**：`backend/app/llm.py` 的 `_call_llm_with_usage()` 在 `create()` 的
> `finally` 里就关闭了 HTTP client，而 `stream=True` 的响应体是**惰性**的 ——
> 套接字在读之前就被关掉，本地 Ollama 的每一次 `/v1` 对话都必然抛
> `httpx.ReadError: [Errno 9] Bad file descriptor`。
> 该异常又被按**类名**归类成「空闲超时」，于是出现
> **0.32 秒返回却写着「300s 无新输出」**的报文，极难定位。
> 修复：把关闭动作移到**流消费之后**。

本缺陷不是本次测试的附带发现 —— 它是**必须先修才能开展本体验证**的硬阻塞：
`/api/chat/compare` 连续 22 例全部 502，本体注入有效性的对照根本跑不起来。

## 1. 现象

| 观察 | 值 |
|---|---|
| 测试首轮 22 例 | **全部 HTTP 502**，无一例外 |
| 单例耗时 | A1 88.6s（3 次重试），A2–A7 均 **~25s**（3 次重试，即每次尝试 ~5s） |
| 后端返回报文 | `模型调用失败：LLM 300s 无新输出（空闲超时），连接可能已中断。` |
| 模型状态 | `ollama ps` → `qwen2.5:32b-32k  28 GB  100% GPU  CONTEXT 32768`（**已加载、完全正常**） |
| 直连 ollama | `curl http://127.0.0.1:11434/api/chat` → **200**；热态连续 3 次 `/v1` 流式请求 TTFB 0.52s / 0.077s / 0.075s，每次约 3s |

矛盾点：**模型是热的、直连是通的，但经后端调用 0.32 秒就失败**，
且报文声称等待了 300 秒。

## 2. 定位过程（三层收敛）

### 第一层：排除「模型慢 / 显存不够」

- `ollama ps` 显示 100% GPU，未回退 CPU；
- `nvidia-smi`（WSL）显示 GPU0 15369/16376 MiB、GPU1 13774/16311 MiB，
  合计约 29.1G / 32.7G，**装得下**；
- 热态直连 `/v1` 每请求约 3 秒。

结论：不是模型侧问题。

### 第二层：抓住「耗时与报文自相矛盾」

用 `curl` 直接打 `/api/chat/compare` 并打印 `-w total`：

```
compare http=502 total=0.323035s
ERROR: 模型调用失败：LLM 300s 无新输出（空闲超时）
```

**0.32 秒的失败不可能是 300 秒超时。** 这句话把排查方向从「网络/模型」扭到
「后端异常分类」。读 `llm.py` 后确认：

```python
if name in ("ReadTimeout", "ConnectTimeout", "ReadError"):
    raise LLMError(
        f"LLM {idle_seconds:.0f}s 无新输出（空闲超时），连接可能已中断。"
        "可在设置页调大「空闲超时」。") from e
```

`idle_seconds` 是**传入的配置值**（300），**不是实际等待时长** ——
报文里的「300s」是常量，不是测量值。任何 `ReadError` 都会被贴上这行文案。

### 第三层：在容器内直调拿原始异常

按项目 README 的只读诊断约定（`docker cp` 到 `/tmp` 再 exec，不写 `backend/`
以免 `--reload` 重启）：

```
docker cp llm_probe.py rag_backend:/tmp/llm_probe.py
docker exec -w /app/backend -e PYTHONPATH=/app/backend rag_backend python /tmp/llm_probe.py
```

拿到堆栈：

```
File "/usr/local/lib/python3.13/site-packages/httpx/_transports/default.py", line 118, in map_httpcore_exceptions
    raise mapped_exc(message) from exc
httpx.ReadError: [Errno 9] Bad file descriptor
...
File "/app/backend/app/llm.py", line 489, in _call_llm_with_usage
    raise LLMError(f"LLM {idle_seconds:.0f}s 无新输出（空闲超时）" ...) from e
app.llm.LLMError: LLM 300s 无新输出（空闲超时），连接可能已中断。
```

**`Bad file descriptor`** —— 套接字已被关闭，却还在读。

## 3. 根因

`_call_llm_with_usage()`（`llm.py:432-454`）原写法：

```python
for attempt in range(1, 4):
    kwargs_client = _http_client_kwargs(s["base_url"], read_timeout=idle_seconds)
    try:
        client = OpenAI(base_url=..., api_key=..., timeout=idle_seconds,
                        max_retries=0, **kwargs_client)
        resp = client.chat.completions.create(**kwargs)   # stream=True → 惰性流
        break
    except Exception as e:
        ...
    finally:
        _close_client_kwargs(kwargs_client)   # ← 问题在这
if last_err is not None and resp is None:
    raise last_err
parts: list[str] = []
for chunk in resp:          # ← 响应体到这里才真正读取，但 client 已经关了
    ...
```

`stream=True` 时 `create()` **不会**读取响应体，只返回一个惰性 `Stream` 对象。
`finally` 紧跟在 `create()` 之后执行，把 client（连带其连接池）关掉；
随后 `for chunk in resp` 一读就 `EBADF`。

### 为什么只有本地 Ollama 中招

`_http_client_kwargs()` 的分支：

```python
if netutil.is_local_url(base_url):
    return {"http_client": httpx.Client(trust_env=False, timeout=...)}   # ← 非空
proxy = _llm_proxy()
if not proxy:
    return {}          # ← 远程直连：空，finally 里 close 是 no-op
```

- **远程通道（V4-Flash / GLM）**：无 `LLM_PROXY` 时返回空 dict →
  `_close_client_kwargs({})` 立即 return，什么都不做 → **掩盖了缺陷**；
- **本地 Ollama**：`base_url = http://127.0.0.1:11434/v1` 命中
  `is_local_url` → 返回一个真实的自定义 client → `finally` 真的把它关了 →
  **100% 必然失败**。

### 讽刺之处

同一文件 `_http_client_kwargs()` 的 docstring 里，作者已经用三组对照实验
明确写下结论（原文摘录）：

> 1. **传 http_client 本身就是风险源** ……
> 2. **直连（不给 client、不设代理）是这里最快最稳的路径**：6/6 OK 且比走代理快 5 倍。

loopback 分支恰恰违背了这条自己总结出的结论；而 `finally` 的提前关闭，
让这个违背从「慢」升级成「全废」。

### 为什么既有测试没抓到

`backend/tests/test_chat.py` 里所有 `provider="ollama"` 的用例都走
`llm._fake_chat_ollama`（测试替身），**从不发起真实 HTTP 流式请求**
（例如 `test_chat.py:186` 的 `chat.answer(..., provider="ollama", ...)`）。
因此这个缺陷在单测里完全不可见 —— 属于「网络路径无测试覆盖」的典型盲区。

## 4. 修复

`backend/app/llm.py`，两处改动，语义不变、只挪动关闭时机：

```python
                finally:
                    # ⚠️ 成功的尝试绝不能在这里关 client：stream=True 返回惰性流，
                    # 响应体要到下方 for chunk in resp 才真正读取。这里 close 等于
                    # 关掉还没读的套接字 → httpx.ReadError: [Errno 9] Bad file
                    # descriptor，并被按类名误报成「300s 空闲超时」。
                    if resp is None:            # ← 只关失败的尝试
                        _close_client_kwargs(kwargs_client)
            if last_err is not None and resp is None:
                raise last_err
            parts: list[str] = []
            try:
                for chunk in resp:
                    ...                     # 原样保留
            finally:
                # 流消费结束（正常读完或中途异常）后才关掉本轮成功的 client。
                _close_client_kwargs(kwargs_client)   # ← 新增
            box["reply"] = "".join(parts)
```

设计取舍：

- **失败的尝试仍立即关闭**：保持原有的「防连接泄漏」意图
  （`_close_client_kwargs` docstring 提到长链路 job 会耗尽代理侧连接容量）；
- **成功的尝试延后到流消费完**：`finally` 同时覆盖「读完」与「中途抛异常」两条路径，
  不留泄漏；
- 不引入 `contextlib.ExitStack` 之类的重构 —— 最小改动，便于 review 与回滚。

## 5. 修复验证

| 验证项 | 修复前 | 修复后 |
|---|---|---|
| 容器内直调 `llm.chat_ollama` | `httpx.ReadError: [Errno 9] Bad file descriptor` | **OK**（返回正常文本） |
| `POST /api/chat/compare` | `http=502 total=0.32s` | **`http=200 total=4.87s`** |
| 左臂（注入本体 17 条）回复 | — | 「本方案的筛选期固定为 **14 天**。」 |
| 右臂（不注入）回复 | — | 「我不确定具体的筛选期天数……您需要查看 CV-202 方案中的详细描述」 |
| 全量 22 例 | 22/22 失败 | 见 `06-指标与结论.md` |

修复后 A/B 立即复现出教科书式的本体效果（左臂答出本体值 14 天，右臂表示
不确定并建议去查方案），说明**本体注入链路本身是好的**，
之前的全灭纯属传输层缺陷。

## 6. 遗留问题（本次未改，建议跟进）

1. **异常分类文案误导**（`llm.py:488-491`）：把 `ReadError` 与
   `ReadTimeout`/`ConnectTimeout` 合并，统一报「{idle_seconds}s 无新输出」。
   `idle_seconds` 是配置常量，不是实际等待时长 —— 这就是「0.3 秒报 300 秒」的来源。
   建议：真实超时（`ReadTimeout`）保留原文案，`ReadError` 单独报
   「流式连接被中断（{实际耗时:.1f}s）」，并在 `_notify` 里带上异常类名。
   **这项会改变既有诊断口径，超出本次范围，未擅自修改。**
2. **网络路径无单测**：`provider="ollama"` 的真实 HTTP 流式路径没有测试覆盖。
   建议补一个用 `http.server` 起本地假流式端点、断言「流读完后 client 才 close」
   的端到端测试，把这类「惰性流 + 提前关闭」问题挡在单测里。
3. 该缺陷与宿主平台无关，**在远程通道上也潜伏着**：一旦某台机器配置了
   `LLM_PROXY`，`_http_client_kwargs` 就会为远端返回自定义 client，
   于是同样的提前关闭会打到 V4-Flash / GLM 上。
