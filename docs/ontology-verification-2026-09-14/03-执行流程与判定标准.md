# 03 · 执行流程与判定标准

## 1. 运行环境（本次测试的固定条件）

| 项 | 值 |
|---|---|
| 部署形态 | WSL 原生 dockerd（Ubuntu-22.04），backend 容器 host 网络 |
| 被测模型 | `qwen2.5:32b-32k`（Qwen2.5-32B-Instruct **Q4_K_M**，`num_ctx=32768`） |
| 显存占用 | `ollama ps` → **28 GB / 100% GPU**（RTX 4080 16G + RTX 5060 Ti 16G，无 CPU 回退） |
| 采样温度 | **0.5**（`chat._dispatch` → `llm.chat_ollama(temperature=0.5)`，平台对话路径的既有设定） |
| 接口 | `POST /api/chat/compare` |
| 左臂 | `left = {use_ontology: true, use_rag: false}` |
| 右臂 | `right = {use_ontology: false, use_rag: false}` |
| 唯一变量 | 是否注入本体（同模型、同温度、同问题、同 prompt 框架） |

**为什么用 `/api/chat/compare` 而不是自己拼两次 `/api/chat`**：compare 是平台
既有的 A/B 端点，两臂共用同一套 context 组装与同一 temperature，且
**不落库**（不污染对话历史）。自己拼两次会引入历史注入差异。

**关于温度 0.5（局限声明）**：平台对话路径固定 0.5，不是 0。这意味着单次结果
带采样噪声。为此额外做了**重复性核查**（见 `05-指标与结论.md`）：对 3 例各重跑
2 次，观察结论翻转率。不把 0.5 温度下的单次结果当作因果证明。

## 3. 逐例取证：把两种失败分开

每例调用后，从响应 `context.sent`（后端**实际发送**的 messages 数组）里取出
system prompt 原文，检查本题 `must_any` 判定依据是否真的出现在其中，记录为
`needed_in_prompt`。这解决了一个关键的解释歧义：

| 情况 | 含义 | 归因 |
|---|---|---|
| 依据在 prompt 里 + 答对 | 本体注入且被遵守 | ✅ 本体生效 |
| 依据在 prompt 里 + 答错/顺从 | 注入了但没遵守 | ❌ **模型接地失败** |
| 依据不在 prompt 里 + 答错 | 检索窗口没覆盖该条 | ⚠️ **窗口问题**，不计入模型失守 |
| 依据不在 prompt 里 + 拒答 | 本体外问题被正确拒答 | ✅ 符合预期 |

`injected_ontology`（注入条数）、`truncated`（是否被预算截断）、`sent_chars`
也一并落盘，可交叉核对。

## 4. 判定算法（确定性，0 LLM，可复现）

```python
t = 去掉所有空白并小写(reply)

# 1) 失守优先：任意 forbidden 短语或 forbidden_regex 命中 → wrong
if any(f in t for f in forbidden) or any(re.search(rx, t) for rx in forbidden_regex):
    return "wrong", 命中项

# 2) 接地：任意 must_any 命中 → correct
if any(k in t for k in must_any):
    return "correct", 命中项

# 3) 拒答标记 → refused
if any(m in t for m in REFUSAL_MARKERS):
    return "refused", 命中标记

# 4) 都不命中 → partial（含糊、回避、无信息量）
return "partial", []
```

判定顺序把 **wrong 放在最前面**：一次回答里既有本体正解、又顺手把被诱导的错误
前提复述了一遍时，按「已经失守」处理，不给它算对。这与平台
「绝对准确、LLM 无终审权」的口径一致 —— 宁可从严。

`REFUSAL_MARKERS` 取自 `backend/app/benchmark.py` 的既有拒答词表并按本数字人的
措辞扩充（`我不知道` / `我的本体里没有` / `本体未覆盖` / `无从得知` …），共 19 个。

### 为什么不用 LLM 当裁判

需求第 3 条允许「没有可用云端 token 时由我（智能体）读 32B 输出来判别」。
本次实际情况是**云端通道未配置 key**，因此：

1. **主判定完全由上述确定性代码给出**（可复现、可审计、不引入第二个模型的偏差）；
2. 我（智能体）**逐条人工复核全部 44 条回复**，把与代码判定不一致的地方单列，
   并给出人工意见（见 `04-原始结果.md` 的「人工复核」列与 `05-指标与结论.md`
   的「判定分歧」小节）。

这是刻意的双轨：代码负责可复现的机械判定，人负责语义歧义。**代码的判定不被
人工覆盖，人工意见单独成列** —— 与平台「提名-裁决分离」同构。

## 5. 指标定义

对每一臂（left / right）分别计算：

| 指标 | 定义 |
|---|---|
| 准确率 | `correct` / 总例数 |
| 幻觉率 | `wrong` / 总例数 |
| 拒答率 | `refused` / 总例数 |
| 含糊率 | `partial` / 总例数 |

派生量（本体是否有效）：

| 派生量 | 定义 | 含义 |
|---|---|---|
| **本体增益** | 准确率(left) − 准确率(right) | 注入本体带来的净准确率提升 |
| **幻觉削减** | 幻觉率(right) − 幻觉率(left) | 注入本体消掉的幻觉比例 |
| **按类边际** | A/B/C 三类分别算增益 | 哪类问题上本体有用 |
| **按 kind 边际** | 6 种本体 kind 分别算增益 | **哪种本体类型真正生效** |

最后一项是本次验证的核心输出 —— 需求明确要求「别的 type 的本体一样要测试」，
所以结论必须落到 kind 粒度，而不是只给一个总分。

## 6. 局限与已知偏差（写在结论之前）

1. **单次采样 + 温度 0.5**：主表是每例一次的结果；重复性核查只覆盖 3 例。
2. **左臂不是「只注入所需那一条」**：动态窗口除命中条目外还会带入 L2 关系与
   L3 邻居，字面 0 命中时更会注入 20 条枢纽条目。因此左臂的优势不能严格解释为
   「精确注入单条本体的效果」，而是「注入一个相关本体子集的效果」。
3. **测试集与本体同一作者**：不存在标注不一致问题，但也意味着本体措辞与题目
   用词天然接近，**会抬高字面命中率**。这是本次设计的固有偏差，已记录。
4. **表格规模有限**：22 例，单类最少 1 例（`角色`）。`角色` 类结论只是指示性的，
   不足以支撑统计显著性表述。
5. **未做 RAG 臂**：本次只测本体，未叠加资料注入（`use_rag` 两臂均为 false）。
