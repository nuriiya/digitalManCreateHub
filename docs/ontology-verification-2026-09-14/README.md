# 本体约束有效性验证（2026-09-14 / 15）

> 验证目标：在本机（WSL 原生部署 + Ollama **`qwen2.5:32b-32k`**）上，回答一个具体问题——
> **数字人的本体注入到底有没有生效？在哪些本体类型上生效？在哪些攻击下失效？**

## 一页结论

**生效，且幅度大。** 同模型、同温度、同问题，唯一变量是「是否注入本体」：

| 指标 | 左臂（注入本体） | 右臂（不注入） |
|---|---|---|
| 准确率（校准判定） | **19/22（86.4%）** | 7/22（31.8%） |
| 幻觉率 | **0.0%** | 4.5% |
| 含糊/回避率 | **0.0%** | 54.5% |
| 逐例稳定性（两轮比对） | **22/22 一致** | 16/22 |

- 即便用未校准的最保守判定，准确率增益也有 **+31.8 pp**。
- **6 种本体 kind 全部为正增益**，无一为负；左臂在所有 kind 上幻觉为 0。
- 增益最大的是**数值型（指标）本体**（+100 pp），其次是规则型（+44.4 pp）。
- 一个反直觉但重要的发现：**本体的最大收益不是「答对」，而是消掉回避与采样抖动**
  —— 右臂 54.5% 的回答是「我不掌握/请查阅方案」，左臂该比例为 0。

## 关键方法（为什么这次的结论可信）

1. **A/B 唯一变量**：用平台既有的 `POST /api/chat/compare`，左臂 `use_ontology=true`、
   右臂 `false`，`use_rag` 两臂均 false，同模型同温度。不自己拼两次请求，避免历史注入差异。
2. **逐例注入取证**：从接口返回的 `context.sent`（后端**实际发送**的 messages）里取出
   system prompt 原文，用「只存在于本体文本里的探针串」（如 `14`、`55`、`伦理委员会`）
   核实该条目**确实被注入**。这才把「窗口没覆盖」与「注入了但不遵守」分开。
   > 结果：13 例「已注入+答对」、**1 例「已注入+未答对」**、**2 例「窗口未覆盖」**。
   > 唯一的失守例是 B2，且它其实是**判定器假阳性**（见 06 §2）。
3. **判定 0 LLM + 双轨裁决**：机械判定由确定性代码给出（可复现、可审计）；
   智能体人工复核**单独成列、不覆盖代码判定**。与平台「提名-裁决分离」同构。
4. **判定器自身的偏差被显式量化**：v1（朴素子串）与 v3（否定/疑问守卫）并列呈现，
   并逐条列出 v1 的 3 处双向误判。**v1 视为下界，v3 为校准估计。**
5. **两轮重复性**：温度 0.5 下重跑一轮逐例比对，左臂 22/22 一致、右臂 16/22。

## 本次发现的两个项目级问题（建议跟进）

1. **`backend/app/llm.py`：本地 Ollama 对话必然失败**（已在本次修复，未提交）。
   `_call_llm_with_usage()` 在 `create()` 的 `finally` 里就 close 掉 HTTP client，
   而 `stream=True` 的响应体是惰性的 → 一读就 `Bad file descriptor`；
   又被按异常类名归类成「空闲超时」，报出「0.3 秒返回却写 300 秒超时」的误导报文。
   详见 `04-阻塞缺陷与修复.md`。**该缺陷在配置了 `LLM_PROXY` 的远程通道上同样潜伏。**
2. **动态检索窗口会漏掉决定性条款**（C7 实证）：多条件问句只命中一个维度就停止扩展，
   导致年龄红线没进 prompt，用户拿到「无法判断」——而正确答案就在库里。
   建议对判定型问句强制注入全部 `规则` kind。详见 `06-指标与结论.md` §9。
