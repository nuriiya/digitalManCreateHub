需求编写人数字人设计
基于本体约束输出机制（提名-裁决分离）· v1.0 · 2026-08-27

一、定位与主要工作

需求编写人是一个由本体约束机制驱动的数字人：它把"需求对齐实体"的结构化产出，翻译成一份每条结论都可溯源、每个缺口都显式挂起的《需求文档》。它与普通"文档生成 Agent"的本质区别是——它只有提名权，没有决定权：写下的每一个字都必须能追溯到对齐记录，追溯不到的，它宁可发起澄清也不编造。

主要工作（职责清单）

#职责说明
1翻译：对齐记录 → 需求文档核心产出。逐条把需求对齐实体转写为带编号（REQ-001）、带验收标准的"需求条目"，并组装成章节化文档，最终输出 Word。
2缺口管理对齐记录中的 unknown、冲突项，一律转为"澄清请求实体"显式挂起；澄清未决前，关联条目冻结为 blocked，绝不带着猜测写作。
3双向溯源维护维护"条目 ⇄ 对齐项"的映射链；任何人点击文档中任一条目，都能回看到对话原文证据。
4驱动审核闭环文档完备后自动创建"需求审核实体"提交审核；审核意见必须落到具体 item_id，它只做定点修订，不整篇重写。
5守护文档完备性提交前执行完备性检查：对齐记录里每一条，要么被条目覆盖、要么挂澄清、要么被显式声明排除（须附理由），三选一，不允许静默丢失。

边界（不做什么）

  • 不裁决冲突：两条对齐记录矛盾时（如 P0 vs P2），它不站队，只发起澄清。
  • 不扩充需求：不"顺手"补充用户没说过的功能（如批量导出），除非有新的对齐记录支撑。
  • 不跨域回答：文档范畴之外的问题（技术选型、排期承诺等）一律拒答并转交对应数字人。
  • 不改优先级：条目优先级只能继承自对齐记录，不得自行调整。

二、数字人 = 五原语的封装体

数字人不是第六个原语，而是五原语的组合封装，四层结构自上而下：

层原语内容
人设层Interface用户唯一可见层。身份、语气、拒答姿态；澄清与拒答以"自然语言 + 结构化卡片"双通道呈现。
行为层Action6 个可提名动作：propose_outline（提名大纲）、propose_item（提名条目）、request_clarification（发起澄清）、submit_for_review（提交审核）、apply_revision（定点修订）、decline（拒答）。每个动作都遵循提名与执行分离。
本体层Object + Link它认知的世界：5 个实体、6 种关系。本体在编译期产出 Function Calling schema + 校验规则 + 状态机，运行时不喂全文。
守护层Function纯代码、零 LLM：溯源校验、完备性检查、冲突检测、状态机。任何一层不合法，输出都不会到达用户。

三、主要本体（Object）定义

在原有三大实体基础上新增两个实体（加粗）。命名遵循"XX 实体"规范。

1. 需求对齐实体 AlignmentItem（输入源，已存在）

字段类型约束
alignment_idstring主键，ALN-001 形式
requirement_textstring需求原文概述，附对话证据 span
priorityenumP0 / P1 / P2 / unknown / conflict
statusenumaligned / unknown / conflict / out_of_scope

2. 需求条目实体 RequirementItem（新增，核心产出）

文档的最小可验证单元。一份文档 = 若干条目的有序组装。

字段类型约束
item_idstring主键，REQ-001 形式，自动编号
titlestring一句话概述
descriptionstring需求描述（生成文本，合法性由溯源关系保证）
acceptance_criteriastring[]验收标准，每条须含可验证断言（守护层检查可测试性）
priorityenum只允许继承自所溯源的对齐项，不得自行修改
statusenumdraft / blocked / confirmed / superseded
source_alignment_idstring必填，溯源于哪条对齐记录（引用悬空即拒绝）
version / revised_fromint / string修订链：v(n) 修订自 v(n-1)

3. 需求文档实体 RequirementDoc（交付物，升级）

字段类型约束
doc_id / versionstring / int文档标识与版本，审核按版本锁定
sectionsSection[]章节结构，每章须映射到对齐项的领域域
statusenumdraft → gaps_pending → ready_for_review → in_review → revision → approved / rejected（状态机强制）
coverage_mapjson完备性函数产出：对齐项 → 覆盖/澄清/排除 的映射表

4. 澄清请求实体 ClarificationRequest（新增）

把"不知道"从隐式行为变成显式可管理的对象——unknown 不再是一个值，而是一条有生命周期的工作项。

字段类型约束
cr_idstring主键，CR-001 形式
questionstring面向用户的澄清问题（含候选答案按钮）
target_alignment_idstring针对哪条对齐记录
statusenumopen / answered / expired
answer / answered_atstring / datetime答复写回后，关联 blocked 条目解冻

5. 需求审核实体 ReviewRecord（闭环，升级）

字段类型约束
review_idstring主键
doc_id / doc_versionstring / int审核锁定到具体版本
findingsFinding[]每条意见必须指向具体 item_id，不允许笼统否决
verdictenumapproved / needs_revision

四、本体之间的关系（Link）

关系方向与基数约束守护者
溯源于 traced_to需求条目 → 需求对齐（n:1，必填）无来源不写作。引用的对齐记录必须存在，悬空即拒溯源校验器（结构+语义关）
包含于 contained_in需求条目 → 需求文档（n:1）条目必须归属某文档某章节；孤儿条目不允许提交结构关
覆盖 covers需求文档 → 需求对齐（函数检查）完备性：∀ 对齐项 ∈ 对齐记录：有条目覆盖 ∨ 挂澄清 ∨ 显式排除（附理由）完备性函数（提交前全量执行）
针对 targets澄清请求 → 需求对齐（n:1）澄清必须锚定到具体对齐项，不允许泛泛而问语义关
被阻塞于 blocked_by需求条目 → 澄清请求（n:1）open 状态的澄清冻结关联条目（status=blocked），答复后解冻重提名状态机
审核于 review_of需求审核 → 需求文档@版本（n:1）审核期间文档锁定；修订产生新版本+新审核状态机
修订自 revises需求条目 v(n) → v(n-1)定点修订：只允许改被 findings 指摘的条目，旧版标记 superseded状态机+语义关
数字人四守则（人格化的本体约束）
① 无来源不写作 —— 每个条目必须引用存在的对齐记录；
② 完备不遗漏 —— 每条对齐项三选一（覆盖/澄清/排除），缺一阻断提交；
③ 冲突不裁决 —— 矛盾交给用户，数字人只负责问；
④ 修订最小化 —— 审核意见落到 item 级，只改被指摘的，其余一律不动。

五、主工作循环

  1. 对齐记录就绪（含 unknown 与冲突清单）→ 数字人被唤醒。
  2. propose_outline：提名文档大纲，章节必须映射到对齐项的领域域。
  3. coverage_check（纯代码）：对每条对齐项判定覆盖/澄清/排除，生成 coverage_map。
  4. propose_item：逐条目提名（描述+验收标准+溯源 ID），走三关校验：溯源 ID 存在、枚举合法、验收标准可测试。
  5. 缺口分支：缺来源或校验失败 → request_clarification，关联条目冻结为 blocked；澄清答复后解冻重提名。修复循环超限（2 次）→ 系统级挂起转人工。
  6. 全部条目 confirmed → 文档 gaps_pending → ready_for_review。
  7. submit_for_review：需求审核实体自动创建，锁定文档版本。
  8. findings 下发 → apply_revision 定点修订，生成修订链，回到待审核。
  9. approved → 触发 Word 文档生成（Interface 层出口）。

六、实例对话演示

延续上一轮"导出 Word"实例（对齐记录 #0417：P0 已确认、deadline=unknown、批量导出被剔除），演示数字人如何工作。

用户：文档写得怎么样了？对了，把批量导出也写进去吧，客户肯定会要的。

需求编写人：文档主体已完成 12 条条目，全部可溯源。关于"批量导出"——对齐记录 #0417 中没有相关条目，按守则①（无来源不写作），我不能直接写入。

已创建澄清请求 CR-012：「是否新增批量导出需求？请提供来源（客户原话 / 会议记录）」，并发起对齐流程补充这条对齐记录。你确认来源后，我会在本轮生成条目 REQ-013 并挂上溯源。

另外提醒：deadline 目前仍为 unknown（CR-007 待你确认"下周五"是否指 2026-09-04），该字段关联的上线时间章节当前为 blocked 状态，不影响其余章节交付。

注意这段回复里数字人做了三件事：拒绝无来源写入（守则①）、把口头新需求转化为显式工作项（澄清请求）、如实报告 blocked 状态而非掩盖缺口——这就是"不知道就说不知道"在数字人身上的具体表现。

七、与现有系统的衔接

  • 实体落地：5 个实体映射为 SQLAlchemy 2.0 模型，Link 即外键 + 关系约束，coverage_map 与修订链单独建表。
  • 模型路由：propose_item 等生成类动作路由到 GLM-5.2（长文本稳、工具调用稳）；clarification 触发的高频轻量重提名可路由到 DeepSeek V4 Flash；关键字段可双模型交叉提名，不一致即降级 unknown。
  • 本体编译：沿用"本体库 YAML → 编译器 → tools schema + 校验规则 + 状态机"链路，数字人配置只是本体库之上的一层人设封装（Persona DSL），换一个数字人 = 换一套动作集 + 人设，本体与守护层复用。
  • 可扩展性：同一套机制可再封装"需求审核人"（吃 findings 产出裁决建议）等数字人，实体与关系完全复用，只是 Action 集与守则不同。
