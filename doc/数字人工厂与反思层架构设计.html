数字人工厂与反思层架构设计

v2.0 · 基于本体约束的数字人自动化创建与自我进化体系 · 2026-08-27

0. 设计目标与决策输入

上一轮设计回答了"如何定义一个数字人"（数字人 = 五原语封装体，需求编写人 = 5 实体 7 关系 + 6 动作 + 4 守则）。本轮回答两个新问题：

  • 自动化创建：如何把"手工定制一个数字人"抽象为可复用的流水线，让创建新数字人 = 写一份声明式基因文件；
  • 诞生后进化：如何增加反思层，在每次对话后自我学习——找可改善点、优化工具链与逻辑、建立用户画像，且全过程不破坏"绝对准确"承诺。

三个策略级决策（已确认）作为架构输入：

决策点选择架构含义
改进如何固化分级审批低风险自动生效，高风险人工队列；裁决依据为回归重放结果
反思用哪个模型混合分工Flash 高频单 Trace 分析 + GLM 周期跨 Trace 归纳，关键提议双模交叉核验
画像深度工作偏好 + 背景推断画像分两组字段分级管控，推断类永不参与本体裁决，需完整隐私策略

1. 总体架构：三层视图

工厂层 Foundry（创建期）→ 运行层 Runtime（对话期）→ 反思层 Reflection（对话后）↺ 回流 Spec（进化期）

三层共用同一条铁律——LLM 永远只有提名权，本体拥有裁决权，代码拥有执行权。工厂层把它用在"造人"上（Spec 提名一个数字人，元本体裁决合法性）；反思层把它用在"学习"上（反思提名改进，回归重放裁决有效性）。机制完全同构，这是本架构最重要的一致性。

核心设计判断：学习成果回流 Spec 层，而非运行时热改。任何时刻，运行中的数字人都是某个确定版本 Spec 的编译产物——可追溯、可复现、可回滚。运行时不允许出现"边跑边改规则"的幽灵状态，否则"绝对准确"就退化成"大概率准确"。

2. 工厂层：数字人是编译出来的

2.1 数字人基因 Spec

每个数字人 = 一份声明式 YAML（约 100–200 行），五个基因段。以需求编写人为例：

spec_version: 1.0
identity:
  name: 需求编写人
  mission: 将需求对齐实体转写为可验证的需求文档
  boundaries: [不裁决冲突, 不扩充需求, 不改优先级, 不跨域]  # 生成 System Prompt 的硬约束段
ontology:                      # 实体依赖声明（复用 > 新增）
  reuse: [需求对齐实体, 需求文档实体, 需求审核实体]
  define:
    - object: 需求条目实体      # 字段表、枚举闭集（同上轮设计）
    - object: 澄清请求实体
  links: [溯源于, 包含于, 覆盖, 针对, 被阻塞于, 审核于, 修订自]
actions:                        # 可提名动作 → 编译为 tools schema
  - name: 撰写需求条目
  - name: 创建澄清请求
  - name: 组装文档并导出 Word
  - name: 发起需求审核
  # ...共 6 个，每个含参数 schema + 前置状态条件
guardians:                      # 守护规则 → 编译为 SHACL + 状态机
  - ref: evidence_span_rule          # 复用全局规则：证据逐字匹配
  - ref: relative_time_forbidden
  - rule: 条目提交前完备性检查（对齐项三选一）
interface:
  tone: 严谨、克制、只陈述可证明的事
  output_cards: [对齐确认卡, 澄清请求卡, 文档预览卡]
  unknown_policy: 显式挂起，绝静默编造

2.2 元本体：约束 Spec 的本体

工厂能自动化的前提是"什么是合法数字人"本身可机器判定。元本体定义 Spec 的合法性约束：

元本体规则约束对象违反后果
identity.mission 与 boundaries 不得语义重叠冲突身份段拒绝创建，要求改写
ontology.reuse 中的实体必须存在于全局本体库且版本兼容本体段拒绝创建，提示版本对齐
actions 中每个动作的参数字段必须能落到某个实体的 schema动作段拒绝创建（防"无本体依据的动作"）
guardians 引用的全局规则 ID 必须真实存在守护段拒绝创建（防引用悬空）
每个 Action 必须声明失败路径（含拒答/转人工出口）动作段拒绝创建（防"无出口死循环"）

自举结构：元本体约束 Spec → Spec 编译出数字人 → 数字人的反思层可以提议改进元本体 → 但元本体改动需最高级别人工审批。工厂编译器本身实现为一个 Function 原语（纯代码、零 LLM），它自己也在本体体系之内，不是体系之外的魔法。

2.3 编译流水线五步

步骤做什么产物 / 出口
① Spec 校验用元本体校验基因文件合法性不合法 → 带原因拒绝
② 本体合并复用实体与新定义实体合并，检测同名异构冲突冲突 → 拒绝，要求显式版本对齐
③ 编译产出同一份 Spec 生成五类产物，保证单一事实源System Prompt 模板 / Function Calling tools schema / SHACL 校验规则 / 状态机转移表 / SQLAlchemy 模型 + Alembic 迁移
④ 冒烟测试跑内置"上岗测试"：一组最小对话样例，验证提名-裁决闭环可走通、拒答路径可用失败 → 拒绝注册
⑤ 版本化注册产物打版本号入库，实例化运行时，自动挂载反思层数字人上线

2.4 版本化与灰度

  • Spec vN → 编译产物 vN，一一对应，git-like 版本链；
  • 修改 Spec（含反思层回流的学习成果）触发重新编译 → vN+1；
  • 灰度切换：新版本接新对话，旧版本实例跑完存量对话后退役；
  • 任何行为异常可整体回滚到 vN——因为运行时状态全部落在实体库里，回滚只回滚"行为逻辑"，不丢数据。

3. 反思层：受提名-裁决约束的自我学习

3.1 五阶段闭环

① Trace 采集→ ② 反思提名（LLM）→ ③ 回归裁决（纯代码）→ ④ 分级固化→ ⑤ 回流 Spec 重编译↺

3.2 Trace：反思的原料

对话轨迹实体（Conversation Trace）是新增的核心 Object。反思层的全部能力上限由 Trace 质量决定。采集内容：

采集项为什么重要
每次 LLM 提名的原始 JSON + 三关裁决结果（通过/打回/拒绝 + 原因）规则缺口与误伤的直接证据
修复循环次数（几次提名才通过）次数高 = 本体规则或 prompt 表述有问题
用户改写 AI 输出的具体位置（diff）黄金信号：模型"以为对了"和"用户认为对"的差距
澄清请求的答复内容与答复率澄清模板化（R3）的依据；反复同类澄清说明本体缺枚举
工具调用延迟、失败率、参数错误工具链优化（R4）的依据
用户表达习惯的原文样本画像构建（R5）的证据来源

3.3 六类改进提议（R1–R6）

反思层的输出是"改进提议实体"（Improvement Proposal）——又一个受本体约束的 Object。每条提议必须引用具体 Trace 证据，否则在结构关即被丢弃（反思的反思：防止反思本身幻觉）。

类型触发信号提议内容风险级
R1 规则缺口某错误输出未被拦截就到达了用户新增守护规则高风险
R2 规则误伤合法输出被拒/被降级 unknown，用户随后确认它本该通过放宽或修订规则高风险
R3 澄清模板化同类澄清请求反复出现且答复一致将答案固化为枚举值/术语表/默认值低风险
R4 工具链优化某动作延迟高、失败率高、参数错误集中调整编排/缓存/参数校验前置高风险
R5 画像信号用户稳定的行为模式（≥3 次一致）画像属性更新提议低风险
R6 用户修正模式用户反复改写同类表述prompt 模板微调 / 输出模板调整高风险

3.4 双模型分工（混合部署落地）

环节模型理由
单 Trace 反思（每次对话后异步触发）DeepSeek V4 Flash高频、低成本、任务结构固定（扫描+分类+引证据）
跨 Trace 归纳（每日/每 N 条批量）GLM 5.2长上下文 + 长程归纳能力强，发现单次看不到的模式
关键提议交叉核验（R1/R2/R4）两模型独立分析同一批 Trace结论不一致 → 提议降级为"待观察"，不进入裁决

注意：反思分析的产出只是提议，即使模型较弱，最坏结果也只是"提议质量低、被回归裁决丢弃"，不会污染运行时——这正是提名-裁决架构对模型质量的容错。

3.5 回归裁决：确定性重放

裁决器在沙箱中把"提议改动后的数字人"对历史 Trace 库整体重放：

  • 必须修复：提议时引用的目标失败案例，重放后变为通过；
  • 不得破坏：所有既有通过案例重放后仍然通过（回归保护）；
  • 一致性检查：新规则不与现有规则集冲突（规则可判定）；
  • 全程零 LLM 参与——重放执行的是纯编译产物。

冷启动问题：初期 Trace 库小，"不得破坏既有案例"的保护覆盖不足，误改规则的风险高。对策：前 N 条（建议 ≥50）改进一律走人工审批，Trace 积累到阈值后再放开低风险自动固化。这是分级审批的时间维度：不只按风险类型分级，还按系统成熟度分级。

3.6 分级审批矩阵

提议类型裁决通过后生效方式
R3 澄清模板 / R5 画像（且系统成熟）自动生效写入 Spec → 定期批量重编译（如每日一次）
R1 / R2 / R4 / R6人工队列审批人看到：提议 + Trace 证据 + 重放前后对比报告 → 一键批准/拒绝/追问
涉及元本体的改动最高审批必须两人复核（架构 Owner + 数字人 Owner）
所有固化产物—全部版本化，可整体回滚

4. 用户画像：受本体约束的个性化

4.1 画像实体结构

用户画像实体（User Profile）同样走提名-裁决：每个属性必须附对话证据 + 置信度，LLM 不能自由发挥画像内容。

字段组内容管控
A 工作偏好（低风险）术语偏好、格式偏好、验收标准写法习惯、澄清答复风格低风险 回归通过自动生效
B 背景推断（高风险）项目背景、组织角色、业务领域高风险 每条附置信度+证据链；仅影响个性化呈现

4.2 生命周期四环

  1. 证据提名：R5 提议画像属性，须引 ≥3 次一致的对话证据；
  2. 运行时应用：画像只注入 Interface 层（术语映射表、格式模板选择、澄清话术风格）——画像只能影响"怎么说"，永远不能影响"什么是对的"。本体裁决路径上不读取画像；
  3. 反馈纠正：用户改写输出即纠正信号，直接更新画像（这是用户亲手给出的真值，无需回归裁决）；
  4. 定期衰减：证据过期（如 90 天）自动降权，防止画像僵化成过时印象。

4.3 隐私与安全边界

  • 透明：画像用户可见——数字人可主动说"我记得你偏好表格呈现，对吗"；
  • 可纠正、可删除：用户可单条修正或整体清空画像，删除即时生效并留审计记录；
  • 用途隔离：背景推断永不参与本体裁决、永不进入需求文档内容本身（防止"迎合画像"污染可验证输出）；
  • 存储策略：画像与 Trace 分库存储，画像表不含对话原文（只存归因结论 + 证据指针）。

5. 新增本体清单

新增实体角色关键关系
数字人规格实体（Persona Spec）数字人的基因，全部行为的唯一事实源编译自 ← 改进提议；版本化为 → 版本实体
对话轨迹实体（Conversation Trace）反思的原料，运行时全程留痕产生于 → 对话；被引用于 → 改进提议 / 画像属性
改进提议实体（Improvement Proposal）反思层的学习提名（R1–R6）引用 → Trace；裁决结果 → 通过/丢弃/待观察；固化后 → 回流 Spec
用户画像实体（User Profile）个性化呈现依据，两组字段分级归属于 → 用户；证据指针 → Trace；衰减于 → 时间
版本实体（Version）所有可固化产物（Spec/规则/模板/画像）的版本锚点锚定 → 任意固化产物；回滚指向 → 前一版本

五原语映射增量：Spec/Trace/提议/画像/版本全部是 Object；"引用/回流/锚定"是 Link；"反思分析、裁决、衰减"是 Function（纯代码）；"审批动作"是 Action（人类执行）；画像注入与审批界面是 Interface。

6. 能力边界（必须诚实告知）

  • 反思看不见没发生过的事：学习完全基于 Trace，Trace 覆盖不到的盲区（如从未被问过的场景）它无法预见。本体设计初期的深层缺陷仍需人工评审发现；
  • 回归测试集本身可能是错的：若历史 Trace 中含未被发现的错误裁决，重放会"保护错误"。缓解：用户改写信号（黄金信号）优先级最高，用户确认过的案例不可被回归裁决否决；
  • 交叉核验成本翻倍：关键提议两模型都跑，延迟与算力×2——仅对 R1/R2/R4 启用；
  • 画像推断可能错：错误画像的个性化反而惹人烦——所以推断必须可纠正、会衰减、只影响呈现；
  • 进化有下限速度：冷启动期（约前 50 条改进）实际是"半自动学习"（全部人工审批），这是安全换速度的刻意选择。

7. 实施路线

阶段范围验收标志
一（先工厂）元本体 v1 + 需求编写人 Spec 化（把上轮手工设计改写为 YAML）+ 编译流水线 + 版本化注册用 Spec 一键编译出等价于上轮手工设计的数字人
二（再反思·只观察）Trace 采集 + Flash 单 Trace 反思 + 提议全部进人工队列（不自动固化）连续 2 周，反思提议的人工采纳率 ≥ 30%
三（开放低风险）回归重放裁决器 + R3/R5 自动固化 + GLM 跨 Trace 归纳 + 画像实体与注入自动固化的低风险改进零事故，回滚演练通过
四（复制造人）用工厂创建第 2 个数字人（建议：需求审核人），验证"换基因不换机制"新数字人 Spec ≤ 200 行，2 天内上线
