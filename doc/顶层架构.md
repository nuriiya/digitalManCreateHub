## 0. 分类轴：本体从哪来

原分类（平台级通用 vs 部门级领域）的表述模糊在「通用」二字——它描述的是**用途**，不能推导出该走哪条创建路径。新分类用**本体段的权威来源**做轴，用途是它的推论。

| 维度 | 基础数字人 | 专业数字人 |
|---|---|---|
| 对应旧命名 | 平台级通用数字人 | 部门级领域专家 |
| 谁提供维护 | 平台方 | 各部门（提供文档与知识包） |
| **ontology 段来源** | **平台通用本体库**（人工定义、封闭、跨部门一致） | **部门文档 → RAG + 本体分解器归纳** |
| 六元语归属 | 六段全部由平台写死，无填位 | 模板写死 identity / reflection / guardians，部门知识包填 ontology / interface / actions |
| 创建路径 | **Spec 编译**（零 RAG） | **知识包合成**（模板 + 部门知识包） |
| 创建入口 | 平台方写 Spec YAML | 部门交文档，平台跑管线 |
| 数量级 | 少（个位数，稳定） | 多（每部门一个，持续增长） |
| 是否带 RAG | **待定**（歧义②） | 是（RAG 就是它的本体来源） |
| 代码状态 | **未实现**（无入口） | **已实现**（rag_prototype 全链路） |

**为什么专业数字人的平台已经建成、基础数字人却没有**：现有 `rag_prototype` 的唯一入口是「文档 → 分段 → 摘要/标签 → EDC 抽取 → 三关校验 → 装配」，这条链的每一环都以「有文档可喂」为前提，天生只能造专业数字人。基础数字人需要另一条不经过 RAG 的路径。

**为什么编译期生成、而不是运行时喂本体提示词**（三条，沿用《本体约束输出架构设计》§03）：
1. 模型永远只见闭集 schema，无法「理解偏」本体；
2. schema / 校验规则 / 状态机同源生成，杜绝双维护漂移；
3. 本体变更 = 重新编译 + 全量回归测试，变更可控。

**元本体的自举结构**：元本体约束 Spec → Spec 编译出数字人 → 数字人的反思层可提议改进元本体 → 但元本体改动需**最高级别人工审批**。编译器本身是一个 Function 原语（纯代码、零 LLM），它自己也在本体体系之内。

## 3. 平台通用本体库

它是基础数字人的 ontology 给养源，也是两类数字人之间唯一的交汇点。

| 特性 | 说明 |
|---|---|
| 手工定义入口 | 研究员/平台方直接写本体条目（名称 / 类型 / 定义 / 适用域 / 严重级别），**落库即生效、即为权威**，不进审批队列 |
| 自适应扩充 | 研究员输入 → LLM 候选提名 → 三关校验（结构闭集 / 语义引用 / 证据 span 逐字命中原文）→ 分级审批 → 版本 v+1。**手写权威高于 LLM 提名** |
| 版本化 + 快照回滚 | 复用现有 `persona_ontology_versions` 机制：变更前快照，任意版本可回滚（回滚前自动再快照，因此回滚本身可逆） |
| 只引用 · 禁改写 | 部门/专业数字人的本体可引用，禁止改写；引用悬空拒绝创建。需 UT 强制 |

**与「监管本体」需求的关系（重要）**：合规守护官的 ontology 段在 pipeline.md §5 中定义为「约束规则 / 合规条款 / 权限边界」，与用户提出的「自定义一批监管本体」高度重合。**监管本体应作为平台通用本体库的第一批内容，两者合并规划，不要建两套。**（关联待办 `re4gXd` 与 `riSzrN`）

## 4. 基础数字人候选清单

**四条判据**（同时满足才算数字人，否则是别的原语）：

1. **跨领域通用**——不随部门变化；
2. **有自有的 ontology 段**——且来源于平台通用本体库；
3. **有提名动作**——会提名，不是纯裁决；
4. **会反思**——有自己的 reflection 触发条件。

> 反例警示：**纯确定性校验是 Function，不是数字人**。三关校验（结构/语义/证据）无状态、可重放、零 LLM，属于 guardians 段，不应被包装成「校验官」数字人。

| 候选 | ontology 段 | 归属 | 依据 / 判断 |
|---|---|---|---|
| 需求分析师 | 需求条目 / 澄清请求 / 提名轨迹 | 基础 | pipeline.md §5；P0 目标数字人 |
| 文档架构师 | 需求文档 / 章节 / 模板 | 基础 | pipeline.md §5；零新增事实，只组装渲染 |
| 合规守护官 | 约束规则 / 合规条款 / 权限边界 | 基础 | pipeline.md §5；**其本体即监管本体** |
| 质量审核官 | 审核记录 / 判定 / 修订链 | 基础 | 路线存档 P1 验收标志「用 Spec 一键编译出第二个数字人（需求审核人）」 |
| 通路编排官 | 通路 / 数字人 / 交接 Link | 基础 | 新需求③ pipeline 的执行者，负责拉起数字人群组 |
| 流程设计师 | 通路 / 编排图 / 数字人 / 交接 Link | 基础 | 2026-09-03 场景新增；负责查通路库、设计编排图、提名所需数字人与工具 |
| 写代码数字人 | 代码结构 / 框架 API / 页面元素 | 基础骨架 + 部门技能包 | 2026-09-03 场景新增；**兼作工具工厂**（见《编排示例-调研并写demo页面.md》§4）。通用语言/框架能力平台写死，部门私有框架以技能包挂载（A-3） |
| 代码复核人 | 代码 / 测试用例 / 缺陷 / 功能点 | 基础 | 2026-09-03 场景新增；复核功能正确性，不通过打回 |

## 5. 专业数字人：现有已实现路径（简述）

完整设计见 `DESIGN_MVP.md` 与 `pipeline.md` §9。链路：

```
部门文档 → ① 分段 + 摘要 + 标签（V4-Flash）→ ② 嵌入 bge-m3 → ③ RAG 知识库
                                            ↘ EDC 抽取 → 定义 → 规范化 → 三关校验 → 分级审批 → 部门专属本体
        → 部门知识包（ontology + interface + actions）→ 与领域专家模板合成 → 审批/测试/迭代闭环
```

### 6.1 已定（2026-09-03）

| 编号 | 歧义 | 结论 | 依据 |
|---|---|---|---|
