本体约束输出架构设计

Ontology-Guarded Generation · 无 RAG · 适用于需求对齐 / 需求文档 / 需求审核三实体 · 基座：GLM-5.2 + DeepSeek V4 Flash
设计信条：凡输出的必可验证，不可验证的必不出。"绝对准确"不是模型属性，而是系统属性——模型只有提名权，本体拥有裁决权，代码拥有执行权。

00设计目标与边界

目标达成手段验收标准
绝对准确闭集 schema 约束 + 三关确定性校验 + 事务执行，错误提名无法到达下游任何落库/出站数据 100% 通过本体校验
不知道就说不知道unknown 是合法枚举值 + 证据绑定 + 拒答 Action + 重试超限兜底无证据字段一律 unknown，系统级拒答路径常开
暂不需要 RAG事实来源只有两个：本次对话上下文 + 本体自身闭集；不检索外部知识库架构中无向量库、无检索组件
为什么"绝对准确"必须靠架构而非模型：LLM 的输出本质是概率采样，任何 prompt 都无法给出硬保证。唯一可行的路径是让"错误的输出"在结构上无法通过校验——用确定性代码（Python，不是 LLM）做最终裁决。这与 Palantir Ontology 的核心理念一致：本体是操作的契约，不是描述性的文档。

01核心原则：提名-裁决分离（Propose-Adjudicate）

  1. LLM 模型只提名：LLM 的唯一职责是从对话中挑选（select）本体允许的值并组装提名（proposal），通过 Function Calling 提交。它不能创造新的实体类型、新的状态值、新的关系类型。
  2. 本体 本体当宪法：本体库是唯一事实源（Single Source of Truth），在编译期（不是运行时）编译成三种产物：JSON Schema 工具定义、SHACL 校验规则、状态机转移表。模型和校验器使用同一份口径。
  3. 证据 证据绑定：LLM 提名的每个事实字段必须附带 evidence——对话原文的逐字引用。校验器做确定性字符串包含检查，无中生有的值在此被拦截。
  4. 拒答 拒答是一等公民："不知道"不是异常路径而是合法输出。宁输出空对象 + unresolved 问题清单，绝不编造填充。

02总体架构（五层）

层职责实现原语归属
L0 对话入口意图路由：判断用户意图映射到哪个 Action 提名FastAPI 端点 + 意图分类（可用轻量规则 + Flash）Interface
L1 受限生成LLM 在闭集 schema 内提名，产出结构化 proposalFunction Calling，tool_choice=required，temperature=0Action（提名）
L2 本体校验三关确定性校验：结构 → 语义 → 证据pydantic + jsonschema + SHACL（pySHACL）+ 自研规则Function
L3 事务执行状态机裁决转移合法性，事务写库SQLAlchemy 2.0 事务 + 状态机转移表Action（执行）
L4 出口网关只有通过全部校验的结构化数据可出站；拒答走专用通道响应模型（response_model）强制约束Interface
关键点：校验层（L2）不含任何 LLM 调用。这是"绝对准确"的根基——裁决逻辑必须是可测试、可复现的确定性代码。LLM 只出现在 L1（提名）与修复循环的回喂环节。

03本体层与编译器

本体库建议用一份声明式 DSL（YAML/Python dataclass）维护，覆盖三实体的类型、属性、关系、状态、基数约束，编译器将其产出三种制品：

ontology/                      # 单一事实源
  entities.yaml                # Object：三实体类型定义 + 属性 + 枚举闭集
  links.yaml                   # Link：关系类型 + 两端类型约束 + 基数
  actions.yaml                 # Action：可提名操作 + 参数 schema + 状态转移
  rules.shacl.ttl              # Function：SHACL 校验规则
compile()  →  tools.json       # 给 L1 的 Function Calling 工具定义
          →  validators.py     # 给 L2 的 pydantic 模型 + 规则注册表
          →  transitions.py    # 给 L3 的状态机转移表
为什么编译期生成而非运行时喂本体提示词：①模型永远只见闭集 schema，无法"理解偏"本体；②schema、校验规则、状态机同源生成，杜绝双维护漂移；③本体变更 = 重新编译 + 全量回归测试，变更可控。

04受限生成层细节

  • 闭集约束：所有枚举字段在 schema 中穷举合法值，并强制 additionalProperties: false——模型发明新字段、新状态值在结构层即被拒绝。
  • 认识论字段：每个可空事实字段都包含 unknown 作为合法枚举值；另设 unresolved 数组承接"对话中缺失、需追问"的信息。模型被明确指示：没有原文依据就填 unknown。
  • 自由文本隔离：叙述性内容只允许出现在指定的 note/description 字段，且永远标记为"模型陈述"（不参与事实校验、不作为下游 Action 的依据）。
  • 采样参数：temperature=0（或极低 top_p），禁用创造性行为；两个基座均 OpenAI 兼容，切换只改 model 名。
  • 不喂本体全文：运行时只喂"当前 Action 的 schema + 少量必要闭集说明"，避免上一轮调研中确认的"全量注入本体导致上下文干扰"问题。

05校验层：三道防线

防线工具拦截什么示例
第一关 · 结构pydantic v2 / jsonschema字段缺失、类型错误、多余字段、枚举外的值priority 不在 {high, medium, low, unknown} 中 → 拒绝
第二关 · 语义SHACL（pySHACL）+ 自研规则类型错配、基数违规、引用完整性、状态转移非法需求审核实体引用了不存在的需求文档 id；status 从 draft 直接跳到 approved
第三关 · 证据确定性 span 匹配（纯字符串操作）无中生有：字段值在对话原文中无逐字依据evidence "用户要求支持离线模式" 在原文中不存在 → 拒绝该字段

三关全部通过才进入 L3；任何一关失败即生成结构化违规报告（哪条规则、哪个字段、期望值集合、实际值），回喂给 L1 修复。

06"不知道"协议（Abstention Protocol）

字段级

  • 所有事实枚举字段含 unknown 合法值；填写 unknown 的字段不参与后续校验，落库时标记 epistemic_status: unknown。
  • evidence 为空数组 → 该字段强制视为 unknown（证据绑定使"编造"与"诚实承认不知道"在结构上可区分）。

实体级

  • 允许提名空对象：{"objects": [], "unresolved": [{"question": "..."}]} 是完全合法的输出。

系统级

  • 专用 Action：declare_insufficient_information——LLM 判断对话信息不足以支撑任何提名时显式调用。
  • 修复循环超限（默认 2 次）后，系统主动拒答并转人工队列；绝不降级为自由文本猜测。
  • Prompt 侧配合：system prompt 明示"你的职责是提名而非回答；宁缺毋滥；unknown 是正确答案而非失败"，并配拒答正例 few-shot。

07修复循环（核心代码骨架）

MAX_RETRY = 2

def guarded_generate(user_msg: str, ontology: Ontology) -> Response:
    tools = ontology.compiled_tools()            # 编译期产物，运行时只读
    msgs = [system_prompt(ontology), user_msg]
    for attempt in range(MAX_RETRY + 1):
        proposal = llm.chat(                      # GLM-5.2 / V4 Flash，OpenAI 兼容
            msgs, tools=tools, tool_choice="required",
            temperature=0,
        )
        report = validator.validate(proposal, ontology)   # 三关，纯确定性代码
        if report.ok:
            return executor.commit(proposal)      # 状态机 + SQLAlchemy 事务
        if attempt == MAX_RETRY:
            return abstain(report)                # 拒答："无法在本体约束下可靠生成"
        msgs.append(tool_feedback(report))        # 结构化违规报告回喂，定向修复

违规报告格式（回喂给模型的内容同样是结构化的，避免二次歧义）：

{
  "violations": [
    {"rule": "sh:closed_enum", "field": "priority",
     "expected": ["high","medium","low","unknown"], "got": "P0",
     "fix_hint": "请从合法值集合中重选，或依据原文填 unknown"}
  ]
}

08与 Palantir 五原语的映射

原语在本架构中的角色落地位置
Object实体类型定义（需求对齐/需求文档/需求审核），编译为 schema definitionsentities.yaml → tools.json
Link关系类型闭集 + 两端类型约束 + 基数 + 引用完整性规则links.yaml → SHACL 规则
ActionLLM 可提名的操作（唯一写入口）；执行由代码状态机裁决，提名与执行分离actions.yaml → tools.json + transitions.py
Function编译器、三关校验器、状态机——全部是纯确定性函数，零 LLMcompile() / validator / executor
Interface对话入口（意图路由）与出口网关（所有出站内容必过校验）L0 / L4

需求审核实体 · 典型校验规则

  • 引用完整性：reviewed_doc_id 必须指向库中已存在的需求文档实体（闭世界）。
  • 结论闭集：verdict ∈ {approved, rejected, needs_changes, unknown}。
  • 基数约束：一份需求文档至多一条生效中的审核记录。
  • 状态机：需求文档 draft → aligned → reviewing → approved / rejected，任何跳跃转移直接拒绝（这正是"需求审核 Action 触发文档状态写回"的运行时闭环）。

10模型路由（结合现有两个基座）

环节推荐基座理由
主编排 / 长程对话 / 文档生成GLM-5.2长程任务稳定性 + 工具调用最稳（Agent 工具最优）
高频实体抽取子调用DeepSeek V4 Flash13B 激活吞吐高、算力省，闭集抽取任务足够
关键字段交叉核验Flash 核 GLM（或反向）两模型独立部署，天然可用于双模型一致性检查（见第 11 节残余风险）

两个模型走同一个 schema 网关：无论哪个模型提名，都必须通过同一份编译期校验规则——切换模型不改架构，这正是 Function 原语"模型无关"的价值。

11准确性边界（诚实清单）

保证级别内容依据
结构 100%不存在 schema 外字段、枚举外取值、类型错误闭集 schema + 第一关校验，数学上封闭
语义 100% 拦截已知违规引用悬空、基数违规、非法状态转移、关系类型错配SHACL 规则逐一声明，可穷举测试
证据级强保证字段值必须有对话原文逐字依据，编造值被拦截span 确定性匹配
残余风险（必须知晓）：① span 真实存在但语义归因错位（如把 A 的话归给 B）——字符串校验拦不住语义错位。缓解：关键字段启用双模型交叉核验（GLM 与 Flash 独立抽取，结果不一致 → 该字段降级 unknown）；② 本体规则自身写错——缓解：本体变更走评审流程（需求审核实体本身就是为此设计），配全量回归测试集；③ LLM 在 evidence 里引用了原文但断章取义——缓解：evidence 强制带位置锚点（消息 id + 起止偏移），校验器按偏移截取比对而非全文搜索。
结论表述：系统保证的不是"模型永不犯错"，而是"模型的错不可能到达下游 + 不可靠时显式说不知道"。这已是工程上"绝对准确"的正确含义。
